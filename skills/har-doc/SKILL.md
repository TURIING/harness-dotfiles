# HAR: 项目知识库
---

项目知识库沉淀"代码里读不到、但对快速理解项目至关重要"的知识。读者是 AI 自己 — 目标是不带任何上下文的新会话，通过 doc/ 就能快速熟悉项目、少走弯路。

**知识库结构**

```
<git 仓库根>/
└── doc/
    ├── index.md          # 注册表：文件 + 一句话说明；含"知识库地图"
    └── <主题>.md          # 主题文档（命名中文/英文均可）
```

**多仓库归属（重要）**

项目由多个 git 仓库组成（主仓库 + 子模块）。知识讲的是哪个仓库的代码/模块/规范，主题文件就放**那个仓库**的 doc/：

- 判断归属：知识指向哪个仓库的代码/模块/规范（如子模块 3rd/Utils、.dsh 各自的知识进它们自己的 doc/，不堆在主仓库）
- 每个 git 仓库的 doc/index.md 都含"知识库地图"，登记"以该仓库为根的目录树"内所有 doc/ 位置（自己 + 子模块）— 子模块可能被其他项目引用，它自己的 index.md 必须自足
- 写入子模块的 doc/ 后：先在该子模块内 git 提交，再回主仓库更新子模块指针（两处都要提交）

**触发时机**

- 用户明确要求归纳（"归纳一下 XXX"、"把这个记录到项目文档"、"更新知识库"）
- 当前对话深入讨论了一个值得沉淀的主题（架构、模块、流程、踩坑），讨论告一段落时
- 用户提问涉及某主题但 doc/ 中还没有对应文档时：先正常回答，再询问是否需要沉淀
- 发现 doc/ 内容与代码现状不符（过期）时：提醒用户可能已过期，可提议更新，**不擅自更新**

**归纳流程**

1. **探索澄清（反问用户，先于一切）**

   不直接开始写。像访谈一样先向用户反问，把要归纳的内容问清楚：
   - 归纳什么主题/知识点？范围多大？
   - 重点偏向哪些方面（业务逻辑 / 实现原理 / 架构 / 概念解释 / 上下游依赖 / 约定与坑）？
   - 新建主题还是归入现有主题？
   - 知识归属哪个仓库？
   一轮不够就多轮，直到用户确认范围。对"讨论中自然冒出的沉淀机会"同样要先确认范围，再继续。

2. **阅读源码（先于动笔）**

   找到主题相关的核心代码并通读实现：源文件、调用点、测试。**不要停留在接口层面** — 只看头文件/签名无法理解"实际怎么运转"，必须读实现代码，理解之后再归纳。归纳内容以代码实况为准，不凭接口臆测行为。

3. **判断归属仓库**

   这个知识点讲的是哪个仓库的代码/模块/规范 → 落到那个仓库的 doc/。

4. **查注册表，确定落点并给出写入方案**

   读目标仓库 doc/index.md，判断知识点能否归入现有主题文件，向用户呈现**写入方案**：
   - 写入位置：哪个仓库的 doc/、哪个文件（现有主题更新 / 新建主题）
   - 内容大纲：计划覆盖哪些章节/要点
   - 若发现现有文档已过期，一并指出过期点与更新方案
   - **等用户明确同意后才进入下一步**；用户提出调整则按意见修改方案

5. **撰写/更新主题文档**（仅经用户明确授权后）

   按下方"主题类型 × 章节"从模板中挑选章节。写完自检：一个没有项目上下文的新 AI 读这份文档，能否快速理解该主题？答案模糊说明信息不足，继续补充。

6. **同步注册表**

   - 新建文件：index.md 表格末尾追加一行（文件 + 一句话说明）
   - 更新文件：说明有变化时同步更新
   - 删除文件：同步删除对应行

7. **确保 AGENTS.md 检索规则存在**

   检查项目根 AGENTS.md 是否已有"提问前先查 index.md、只读相关主题"的规则；没有则添加（AGENTS.md 不存在时创建它）。多仓库时规则应体现：主仓库 index.md 是总入口，用知识库地图定位仓库。

**主题类型 × 章节（工具箱）**

不是每个主题都要写满模板全部章节 — 按主题类型挑章节，避免空章节：

| 主题类型 | 典型问题 | 核心章节 |
|---------|---------|---------|
| 架构总览 | 系统怎么组织的 | 背景与定位、架构与原理、上下游依赖、关键代码位置 |
| 模块/组件 | 这个模块怎么运转 | 背景、核心概念、原理、业务逻辑、依赖、坑、锚点 |
| 概念/术语 | 这个词什么意思 | 核心概念为主（+背景） |
| 流程/场景 | 一条链路怎么走完 | 业务逻辑、上下游依赖、注意事项与坑 |
| 约定/规范 | 这里有什么潜规则 | 注意事项与坑、关键代码位置 |

**内容侧重点**（通用，适用于任何项目）

优先写 — 按价值排序：

1. **业务逻辑与流程**：模块在做什么、状态怎么流转、业务规则与边界
2. **实现原理与机制**：核心实现思路，而非代码复述
3. **架构与结构**：分层、模块划分、主数据流、生命周期
4. **概念解释**：领域术语、内部黑话、核心抽象（AI 最缺上下文的地方）
5. **上下游依赖**：模块间依赖、调用链入口、外部依赖
6. **约定与坑**：隐式约定、调用顺序、线程模型、生命周期、已知坑

原则：**离代码越远、越"读不到"的知识越优先写**。

**主题文档模板**

```markdown
# <主题名>

> 一句话概述：这是什么、解决什么问题

## 背景与定位
为什么存在、在项目中的位置

## 核心概念
关键术语与概念解释（AI 最缺上下文的地方）

## 架构与原理
整体结构、实现原理、关键机制（用列表/文字图描述层次与关系）

## 业务逻辑
主要流程、状态流转、业务规则

## 上下游依赖
- 上游：依赖什么（模块、数据、服务）
- 下游：谁依赖它

## 关键代码位置
| 关注点 | 位置（文件/函数） |
|--------|------------------|

## 注意事项与坑
隐式约定：调用顺序、线程模型、生命周期、初始化依赖、常见错误

## 相关主题
- [主题](文件.md)
```

**避免写**

- 复述代码、API 签名、语法细节（AI 自己会读代码）
- 显而易见的文件/目录清单
- 流水账式的对话记录
- 大段复制粘贴的代码
- 无事实依据的主观评价
- 不确定的内容不标注（标"待确认"，不编造）

**写作要点**

- 结构一致，方便 AI 快速扫描
- 主题文件之间用相对链接互相引用，形成知识网络
- 信息密度优先：短句、要点化
- 内容来自对源码实现的阅读，不凭接口臆测

**护栏**

- 不擅自创建主题：用户指定，或从讨论中提炼时先征得用户同意
- 更新已有主题前先读原文件，保留有价值内容，避免覆盖
- index.md 是唯一注册入口，主题文件的新增/删除/更名必须同步 index.md
- 文档主要给 AI 读，但也可能被人类阅读：保持中文、条理清晰
- **过期处理**：发现已有文档与代码现状不符时，先指出过期点并提醒用户，征得同意后才更新，绝不擅自改
- **与 har/specs 相互独立**：doc 不引用、不同步 spec，spec 也不驱动 doc
- **文档归属**：主题文件必须落在知识归属仓库的 doc/ 下，不跨仓库堆放
